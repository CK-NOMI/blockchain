## 一、概述

本文档详细阐述农产品供应链溯源系统中**物流模块**（5个页面）和**零售模块**（6个页面）接入 FISCO BCOS 区块链的完整技术方案，涵盖智能合约、Node.js 后端、Vue 3 前端三层架构的实现细节、数据流转路径和部署步骤，供团队其他成员参考和后续维护使用。

### 1.1 项目背景

本项目是一个基于 FISCO BCOS 联盟链的农产品供应链溯源系统，覆盖六大角色（管理员、农户、加工方、物流方、零售方、监管方）和消费者查询端。本模块负责物流运输和零售入库/销售两个核心供应链环节的链上存证。

### 1.2 技术栈总览

| 层级 | 技术 | 版本 |
|------|------|------|
| 区块链 | FISCO BCOS (PBFT共识) | v3.11.0 |
| 智能合约 | Solidity (EVM兼容) | 0.8.x |
| 链交互 | ethers.js + JSON-RPC | v6 |
| 后端 | Node.js + Express | 18+ |
| 前端 | Vue 3 + Vite + Pinia | 3.x |
| 合约部署 | ethers.js Script | v6 |

### 3.2 批次状态枚举 (BatchStatus)

状态码定义在 `TraceManager.sol` 中，是贯穿整个系统的核心数据模型：

```
状态码  枚举值          中文名称      触发合约方法          操作角色
──────────────────────────────────────────────────────────────
  0    Created          已创建        createBatch()         农户
  1    Farming          农事中        addFarmRecord()       农户
  2    Submitted        已提交加工     addFarmRecord()       农户
  3    Processing       加工中        addProcessRecord()    加工方
  4    Processed        已加工        addProcessRecord()    加工方
  5    Transporting     运输中    ←─  addLogisticsRecord()  物流方
  6    Delivered        已送达        updateBatchStatus()   物流方
  7    Stored           已入库    ←─  addRetailRecord()     零售方
  8    OnSale           已上架        updateBatchStatus()   零售方
  9    SoldOut          已售罄        updateBatchStatus()   零售方
 10    Abnormal         异常          markAbnormal()        监管方
```

### 3.3 物流与零售相关数据结构

```solidity
// 物流运输记录
struct LogisticsRecord {
    string vehicleInfo;    // 车辆信息 (车型|车牌|司机)
    string routeInfo;      // 路线信息 (出发地→目的地|时间)
    string tempHumidity;   // 温湿度JSON数据
    string fileHash;       // 附件哈希 (IPFS/SHA-256)

    string saleStatus;     // 销售状态描述
    string fileHash;       // 验收报告哈希
    uint256 timestamp;     // 毫秒时间戳
    address operator;      // 操作者地址
```

### 3.4 核心合约方法

#### addLogisticsRecord（物流运输记录上链）

```solidity
function addLogisticsRecord(
    string memory batchId,
    string memory vehicleInfo,
    string memory routeInfo,
    string memory tempHumidity,
    string memory fileHash
) external batchExists(batchId) onlyLogistics {
    // 前置条件：批次状态必须为 Processed(4) 或 Transporting(5)
    require(
        batches[batchId].status == BatchStatus.Processed ||
        batches[batchId].status == BatchStatus.Transporting,
        "Batch not ready for logistics"
    );
    // 推入记录数组，自动切换状态为 Transporting(5)
    logisticsRecords[batchId].push(LogisticsRecord(...));
    batches[batchId].status = BatchStatus.Transporting;
    emit LogisticsRecordAdded(batchId, vehicleInfo, msg.sender);
}
```

#### addRetailRecord（零售入库验收上链）

```solidity
function addRetailRecord(
    string memory batchId,
    string memory storeLocation,
    string memory saleStatus,
    string memory fileHash
) external batchExists(batchId) onlyRetail {
    // 前置条件：批次状态必须为 Delivered(6) 或 Stored(7)
    require(
        batches[batchId].status == BatchStatus.Delivered ||
        batches[batchId].status == BatchStatus.Stored,
        "Batch not ready for retail"
    );
    // 推入记录数组，自动切换状态为 Stored(7)
    retailRecords[batchId].push(RetailRecord(...));
    batches[batchId].status = BatchStatus.Stored;
    emit RetailRecordAdded(batchId, storeLocation, msg.sender);
}
```

#### updateBatchStatus（手动状态切换）

```solidity
function updateBatchStatus(string memory batchId, uint8 newStatus)
    external batchExists(batchId) {
    // 无角色限制——由后端 roleGuard 中间件控制
    batches[batchId].status = BatchStatus(newStatus);
    emit BatchStatusChanged(batchId, newStatus, msg.sender);
}
```

### 3.5 权限控制策略

- **合约层**：每个方法有对应的 Solidity modifier（`onlyLogistics`、`onlyRetail`），通过跨合约调用 `RoleManager` 验证调用者角色
- **管理员绕过**：所有 modifier 均包含 `msg.sender == roleManager.admin()` 判断，允许系统管理员账户执行任何操作
- **后端层**：JWT 鉴权 + roleGuard 中间件二次校验（`logisticsGuard`、`retailGuard`），ADMIN 角色同样可以绕过

### 4.2 fiscoClient.js — JSON-RPC 封装核心

这是整个后端与区块链交互的核心层。FISCO BCOS v3 与以太坊有两个关键差异：

| 差异点 | 以太坊 | FISCO BCOS v3 |
|--------|--------|---------------|
| 时间戳单位 | 秒 (seconds) | **毫秒 (milliseconds)** |
| Gas机制 | 按gas计费 | **免费 (gasPrice=0)** |
| 交易格式 | EIP-1559 (type:2) | **Legacy (type:0)** |
| chainId | 1 (主网) | **20200 (默认)** |

**关键实现细节：**

```javascript
// 交易参数固化
const tx = {
    type: 0,             // FISCO BCOS要求Legacy交易格式
    gasPrice: 0,         // 免费Gas
    gasLimit: 30000000,  // 固定Gas上限
    chainId: config.fisco.chainId,  // 20200
    nonce: await this.rpc('eth_getTransactionCount', [wallet.address, 'latest']),
    to: contractAddress,
    data: iface.encodeFunctionData(method, args),
};

// 签名+发送+等待收据循环
const signedTx = await wallet.signTransaction(tx);
const txHash = await this.rpc('eth_sendRawTransaction', [signedTx]);
// 轮询30次，每次间隔1秒
for (let i = 0; i < 30; i++) {
    const receipt = await this.rpc('eth_getTransactionReceipt', [txHash]);
    if (receipt) {
        if (receipt.status === '0x0') throw new Error('Transaction reverted');
        return receipt;
    }
    await new Promise(r => setTimeout(r, 1000));
}
```

**只读调用 (callReadOnly) 流程：**
1. 根据合约名查找 ABI 和地址
2. `ethers.Interface` 对方法+参数进行 ABI 编码
3. 通过 `eth_call` JSON-RPC 发送
4. 对返回的 hex 数据进行 ABI 解码
5. 如果只有一个返回值，直接展平返回

**多节点容错：** 构造函数接收 RPC URL 数组，默认连接第一个可用节点 (`http://127.0.0.1:8545`)，后续可扩展为故障切换。

### 4.5 鉴权体系

```
用户登录 → POST /api/auth/login → JWT Token (7天有效)
    ↓
每次请求 → Authorization: Bearer <token>
    ↓
auth.js 中间件 → 验证Token → req.user = { address, role, username }
    ↓
roleGuard.js 中间件 → req.user.role 匹配 or ADMIN 绕过
    ↓
controller → traceService → fiscoClient → 区块链交易
```

### 5.1 HTTP 层设计

`src/services/http.js` 是整个前端的数据入口，包含两个关键拦截器：

**请求拦截器 → 自动登录：**
```javascript
// 1. 检测 localStorage 中 token 是否存在
// 2. 不存在则根据当前用户角色自动调用 POST /api/auth/login
// 3. 获取真实JWT token后附加到请求头
// 4. 使用防重入Promise避免并发请求重复登录
http.interceptors.request.use(async (config) => {
    const token = await ensureToken();
    if (token) config.headers.Authorization = `Bearer ${token}`;
    return config;
});
```

**响应拦截器 → 解包envelope：**
```javascript
// 后端返回 { code: 0, data: ..., msg: "ok" }
// 拦截器自动提取 data，使调用方直接拿到业务数据
http.interceptors.response.use((response) => {
    const body = response.data;
    if (body && typeof body.code === 'number') {
        if (body.code === 0) return body.data;  // 成功→返回data
        throw new Error(body.msg);              // 失败→抛异常
    }
    return response;
});
```

### 6.1 物流模块操作流程

```
步骤1：物流方登录 → /logistics/dashboard
  │  调用 GET /api/batches/dashboard?role=LOGISTICS
  │  后端筛选状态 4-6 的批次 (Processed→Delivered)

  │
  ▼
步骤2：点击"接收任务" → /logistics/transport-record/:batchId
  │  填写车辆信息 (车型、车牌、司机、电话)
  │  填写运输路线 (出发地、目的地、时间)
  │  点击"提交上链" →
  │    POST /api/batches/:batchId/logistics-record
  │    → traceService.addLogisticsRecord()
  │    → fiscoClient.callContract('TraceManager', 'addLogisticsRecord', [...])
  │    → 合约验证状态为Processed或Transporting
  │    → 推入logisticsRecords数组
  │    → 自动切换状态为Transporting(5)
  │    → 返回交易哈希，显示在链上状态卡片中
  │
  ▼
步骤3：跳转 → /logistics/temp-record/:batchId
  │  设置温湿度阈值 (默认2~8°C, 40~80%)
  │  添加运输节点 (时间、地点、温度、湿度、类型)
  │  异常自动检测 (超出阈值变红)
  │  点击"提交上链" →
  │    将nodes数组序列化为JSON存入tempHumidity字段
  │    再次调用 addLogisticsRecord
  │    vehicleInfo改为 "节点数:N | 异常:M"
  │
  ▼
步骤4：跳转 → /logistics/batch-detail/:batchId
  │  展示全链路时间线 (农事→加工→物流)
  │  显示交易哈希、链上状态、文件哈希
  │  物流方可手动更新状态为 Delivered(6)
  │
  ▼
完成：批次状态=Delivered(6)，进入零售方可见范围
```


| 消费者 | 只读 | 任何状态 | — | 扫码查溯源 |

### 7.2 农户端对接

农户端负责创建批次并录入农事记录，是整个供应链的数据源头。

#### 7.2.1 创建批次

```http
POST /api/batches/create
Authorization: Bearer <JWT_TOKEN>
Content-Type: application/json

{
  "batchId": "SC20240521001",    // 批次号，唯一标识
  "productName": "有机葡萄",      // 产品名称
  "origin": "新疆吐鲁番",         // 产地
  "category": "水果",            // 品类
  "quantity": "1000"             // 数量（纯数字字符串，勿带单位如"箱"）
}
```

**成功响应：**
```json
{
  "code": 0,
  "data": {
    "batchId": "SC20240521001",
    "txHash": "0x28ceba655adc81c19da458ac9f4c8baad3cd20067...",
    "blockNumber": 66
  },
  "msg": "批次创建成功"
}
```

**合约动作：** `TraceManager.createBatch()` → 状态为 Created(0)，发出 `BatchCreated` 事件。

**Vue 3 前端调用示例：**
```javascript
// 在农户 store 中
import http from '@/services/http'

async function createBatch(batchId, productName, origin, category, quantity) {
  const res = await http.post('/api/batches/create', {
    batchId, productName, origin, category, quantity: String(quantity)
  })
  return res.data  // { batchId, txHash, blockNumber }
}
```

#### 7.2.2 添加农事记录

```http
POST /api/batches/:batchId/farm-record
Authorization: Bearer <JWT_TOKEN>
Content-Type: application/json

{
  "recordType": "播种",                                     // 记录类型
  "description": "春季播种，有机种子，播种面积50亩",          // 详细描述
  "fileHash": "QmFarmSeed001"                              // 附件哈希（可选，无则传空字符串）
}
```

**合约动作：** `TraceManager.addFarmRecord()` → 首次调用状态变为 Farming(1)，推入 `farmRecords` 数组。

**完整农户流程（3步农事记录）：**

### 7.3 加工端对接

加工端从农户接收 Submitted(2) 状态的批次进行加工。

#### 前置条件检查
加工端应先调用 Dashboard API 查询自己可见的批次：

```http
GET /api/batches/dashboard?role=PROCESSOR
Authorization: Bearer <JWT_TOKEN>
```
返回状态在 2-4 范围内的批次列表（Submitted → Processed）。

#### 7.3.1 添加加工记录

```http
POST /api/batches/:batchId/process-record
Authorization: Bearer <JWT_TOKEN>
Content-Type: application/json

{
  "processType": "清洗分拣",                    // 加工类型
  "description": "高压水洗+人工分拣",            // 详细描述
  "reportHash": "QmProc001"                    // 质检报告哈希（可选）
}
```

**合约动作：** `TraceManager.addProcessRecord()` → 首次调用状态变为 Processing(3)，推入 `processRecords` 数组。

#### 7.3.2 加工完成后切换状态

```http
PUT /api/batches/:batchId/status
Authorization: Bearer <JWT_TOKEN>
Content-Type: application/json

{ "status": 4 }
```

**关键操作：** 将状态切换为 **Processed(4)** 后，批次将自动出现在物流方 Dashboard 中。这是对接物流模块的唯一必要条件。

**完整加工流程：**
```bash

  -H "Authorization: Bearer $TOKEN" \
  -H "Content-Type: application/json" \
  -d '{"processType":"清洗分拣","description":"高压水洗+人工分拣","reportHash":"QmProcClean001"}'

# 2. 质检
curl -X POST http://127.0.0.1:3001/api/batches/MY-BATCH-001/process-record \
  -H "Authorization: Bearer $TOKEN" \
  -H "Content-Type: application/json" \
  -d '{"processType":"质量检测","description":"农残检测合格","reportHash":"QmProcQc001"}'

# 3. 标记加工完成 → 状态变为 Processed(4)，物流方可接收
curl -X PUT http://127.0.0.1:3001/api/batches/MY-BATCH-001/status \
  -H "Authorization: Bearer $TOKEN" \
  -H "Content-Type: application/json" \
  -d '{"status":4}'
```

#### 7.7.3 前端自动登录（开发模式）

```javascript

  id: 'dev',
  username: '开发者',
  role: 'FARMER'  // 或 PROCESSOR / LOGISTICS / RETAIL / ADMIN / REGULATOR
}))
localStorage.removeItem('token')  // 清除旧Token触发自动登录
```

**路由也会自动处理角色——** 访问 `/farmer/dashboard` 自动以农户身份登录，访问 `/retail/dashboard` 自动以零售方身份登录。

### 7.8 API 通用规范

#### 7.8.1 响应格式

所有 API 统一返回：
```json
{
  "code": 0,       // 0=成功，非0=错误码
  "data": { ... }, // 业务数据
  "msg": "ok"      // 提示信息（中文）
}
```

**错误响应示例：**
```json
{
  "code": 401,
  "data": null,
  "msg": "登录已过期，请重新登录"
}
```

#### 7.8.2 重要注意事项

1. **数量字段 `quantity` 必须是纯数字字符串**，如 `"500"`，不能带单位（`"500箱"` 会导致链上交易失败）
2. **中文编码**：使用 Node.js HTTP 客户端或 Postman 发送中文数据，避免使用 curl（可能导致乱码）
3. **状态切换**：只有 `updateBatchStatus` 接口可以手动变更状态，其他方法自动推进状态
4. **角色权限**：后端 JWT 中的 `role` 字段决定可调用的接口，ADMIN 角色可调用所有接口
5. **交易确认**：每个写操作（POST/PUT）都会等待链上交易确认（最长30秒），成功后返回 `txHash` 和 `blockNumber`

## 十、关键技术决策与注意事项

### 10.1 为什么使用毫秒时间戳

FISCO BCOS v3 与以太坊不同，`block.timestamp` 返回毫秒而非秒。**如果后端代码中使用 `new Date(timestamp * 1000)` 会导致日期变成 "+058350-07-20"**，必须直接使用 `new Date(Number(timestamp))`。

### 10.2 为什么使用 Legacy 交易格式

FISCO BCOS 的地址恢复算法与以太坊 EIP-1559 交易不完全兼容。使用 `type: 0` (Legacy) 可保证 `ecrecover` 正确恢复签名者地址。

### 10.3 Gas 免费机制

FISCO BCOS 默认配置 `gasPrice=0`，不需要原生代币即可发送交易。gasLimit 设置为 30000000 以覆盖复杂合约调用的计算消耗。

### 10.4 管理员绕过设计

合约层所有 modifier 均允许 `roleManager.admin()` 绕过角色检查，后端 `roleGuard` 也允许 `ADMIN` 角色访问所有接口。这保证了管理员可以代理任何角色的操作（如调试、数据修复）。

### 10.5 登录页不可修改

登录页（`/login`）及其相关公共页面（注册、审核中、403/404、退出确认）的路由保持使用 `PrototypeFrameView` 加载 HTML 原型，**不允许替换为 Vue 组件**。这是团队协作的边界约定，确保其他组员负责的首页部分不被覆盖。

### 10.6 开发模式自动登录

开发模式下（`import.meta.env.DEV === true`），前端会根据 URL 路径前缀自动判定角色并调用后端登录 API 获取真实 JWT Token，无需手动登录：

```javascript
// router/index.js - 开发模式路由守卫
if (isDev) {
    const role = neededRole(to.path) || 'LOGISTICS';
    if (user.role !== role) {
        localStorage.setItem('user', JSON.stringify({ id: 'dev', username: '开发者', role }));
        localStorage.removeItem('token');  // 触发 http.js 拦截器自动登录
    }
    next();
}
```

**因此开发时直接访问 `http://localhost:5173/logistics/dashboard` 即可自动以物流方身份登录。**

以下文件已加入 `.gitignore`，**禁止提交到版本库**：
- `.env` / `agrichain-backend/.env` — 含合约地址和私钥

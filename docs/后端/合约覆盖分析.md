## TraceManager 状态机设计

#### 2.1 设计原则

合约采用 **"粗粒度里程碑 + uint8 灵活范围"** 的混合模式：

- 合约只记录业务流程的 **关键里程碑**（农事→加工→物流→零售→售罄/过期）
- 后端维护 **细粒度业务状态**（11-12 个展示状态）
- 合约状态通过 `CONTRACT_TO_BUSINESS_STATUS` 映射到后端业务状态
- `changeBatchState` **不做硬范围约束**，支持开发阶段状态值变动

#### 2.2 状态常量定义

```solidity
uint8 constant STATE_CREATED           = 0;  // 批次已创建
uint8 constant STATE_FARM_RECORDED     = 1;  // 农事记录完成
uint8 constant STATE_PROCESS_RECORDED  = 2;  // 加工质检完成
uint8 constant STATE_LOGISTICS_RECORDED = 3; // 物流运输完成
uint8 constant STATE_RETAIL_RECORDED   = 4;  // 零售上架
uint8 constant STATE_EXPIRED           = 5;  // 过期未售（异常终态）
uint8 constant STATE_SOLD              = 6;  // 正常售罄（正常终态）
```

> **为什么用 `uint8` 常量而不是 `enum`？**
>
> Solidity 的 `enum` 在值越界时（如 `State(6)`）会触发 `BadInstruction` 导致交易回滚。用 `uint8` 常量可以在保留可读性的同时，允许后端传入扩展的状态值，避免因需求变动反复重部署合约。

#### 2.3 状态跃迁规则

```
                                    ┌→ STATE_SOLD(6)  正常售罄
STATE_CREATED(0) ─→ STATE_FARM_RECORDED(1) ─→ STATE_PROCESS_RECORDED(2) ─→ STATE_LOGISTICS_RECORDED(3) ─→ STATE_RETAIL_RECORDED(4) ─┤
                                                                                                                                    └→ STATE_EXPIRED(5)  过期未售
```

| 当前状态 | 下一状态 | 触发函数 | 角色 |
|---------|---------|---------|------|
| — | STATE_FARM_RECORDED | `createBatch` | 农户（role 1） |
| 任意（≠Expired） | STATE_FARM_RECORDED | `recordFarmInfo` | 农户（role 1） |
| = STATE_FARM_RECORDED | STATE_PROCESS_RECORDED | `recordProcessInfo` | 加工商（role 2） |
| = STATE_PROCESS_RECORDED | STATE_LOGISTICS_RECORDED | `recordLogisticsInfo` | 物流商（role 3） |
| = STATE_LOGISTICS_RECORDED | STATE_RETAIL_RECORDED | `recordRetailInfo` | 零售商（role 4） |
| 任意 | 任意 | `changeBatchState` | 零售商（role 4）/ 监管员（role 5） |

> **注意**：`createBatch` 创建批次后直接进入 `STATE_FARM_RECORDED`(1)，跳过了 `STATE_CREATED`(0)。`STATE_CREATED` 作为预留起始值，用于区分"批次不存在"和"批次刚创建"。

#### 2.4 合约状态 → 后端业务状态映射

```javascript
// traceService.js
const CONTRACT_TO_BUSINESS_STATUS = [0, 1, 4, 5, 8, 10, 9];
// 索引:   0   1  2  3  4   5  6
// 解释:  Created, Farming, Processed, Transporting, OnSale, Expired, SoldOut
```

| 合约值 | 合约常量 | 业务值 | 业务显示名 |
|:-----:|:---------|:-----:|:----------|
| 0 | STATE_CREATED | 0 | Created |
| 1 | STATE_FARM_RECORDED | 1 | Farming |
| 2 | STATE_PROCESS_RECORDED | 4 | Processed |
| 3 | STATE_LOGISTICS_RECORDED | 5 | Transporting |
| 4 | STATE_RETAIL_RECORDED | 8 | OnSale |
| 5 | STATE_EXPIRED | 10 | Expired |
| 6 | STATE_SOLD | 9 | SoldOut |

后端完整业务状态表（12 个状态，0-11）：

```
0  Created      批次已创建
1  Farming      种植中
2  Submitted    已提交待加工
3  Processing   加工中
4  Processed    已加工
5  Transporting 运输中
6  Delivered    已送达
7  Stored       已入库
8  OnSale       在售
9  SoldOut      售罄
10 Expired      过期未售
11 Abnormal     异常
```

#### 2.5 角色分发池

各角色工作台按业务状态范围过滤可见批次：

| 角色 | 业务状态范围 | 可见批次 |
|:-----|:-----------|:---------|
| FARMER | 0-2 | Created ~ Submitted |
| PROCESSOR | 2-4 | Submitted ~ Processed |
| LOGISTICS | 4-6 | Processed ~ Delivered |
| RETAIL | 6-8 | Delivered ~ OnSale |

#### 2.6 changeBatchState 设计

`changeBatchState` 是一个通用状态写入函数，不做硬范围校验：

```solidity
function changeBatchState(bytes32 _batchId, uint8 _state) public onlyRole(4) {
    require(batches[_batchId].batchId != bytes32(0), "Batch missing");
    batches[_batchId].currentState = _state;
}
```

- **权限**：仅零售商（role 4）可调用（使用 `onlyRole` 修饰器而非行内 `||`，因 Solidity 0.4.25 编译器在 `||` 连接外部合约调用时有 bug，详见《合约调用指南.md》2.1 节）
- **范围**：不做硬约束——项目仍在开发阶段，状态值可能变动
- **用途**：后端 `updateBatchStatus` 和 `markBatchAbnormal` 两个 API 都调此函数

### 注意事项

- **签名架构规则**：所有需要合约权限修饰符（onlyRegulator / onlyFarmer 等）的写函数，后端必须使用 `callContractAs(wallet, ...)` 传入用户地址，而非使用 `callContract(...)`（会用系统钱包 / 部署者地址）。这是 FISCO BCOS 通过 WeBASE-Front 签名转发的架构约束。
- **平行数组转换**：Solidity 0.4.x 不支持返回结构体数组，合约 getter 使用平行数组（多个 `string[]` / `address[]` 返回值），由后端 `auditService.js` 转换为对象数组供 controller 消费。
- **solc 编译方式**：合约编译部署必须使用 FISCO 控制台（`bash console.sh deploy`）或 WeBASE-Front 网页 IDE。控制台使用自带的 Solidity 编译器，与合约使用的 `pragma solidity ^0.4.25` 兼容。**禁止**通过 npm `solc` 包本地编译（`solc@0.4.25` 与 Node v22 不兼容，而 `solc@0.8.x` 不兼容 `pragma solidity ^0.4.25` 语法），详见《合约调用指南.md》第一章。

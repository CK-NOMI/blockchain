\begin{abstract}
本文不是第九周汇报用的“系统设计说明”，而是一份面向后续真实开发落地的技术实现方案。文档目标是把“接下来每一阶段到底要做什么、用什么工具、先做哪一步、后做哪一步、每一步的产出是什么、做到什么程度算完成”讲清楚，让小组成员可以直接按照本文推进开发。方案围绕“基于 FISCO BCOS 的农产品供应链溯源系统”展开，以农户、加工中心、冷链物流、超市零售、消费者、监管员六类角色为业务主体，以 BatchID 为核心业务对象，以“关键数据上链、附件链下存储、哈希上链锚定、状态机控制流转、前后端协同展示”为总体实现主线。本文重点给出：工程落地原则、环境准备、工具链、项目目录结构、阶段拆分、角色分工、合约实现顺序、后端接口实现顺序、前端页面实现顺序、联调与测试方式、演示准备方法、验收标准、风险应对及 1 号总控同学的推进清单。本文可以直接作为团队后续开发执行文档，也可以作为 Overleaf 中的正式实现方案章节使用。
\end{abstract}

\section{文档定位与使用方式}

\subsection{本文档解决什么问题}

前一份系统设计报告主要回答“为什么这样设计”“系统架构是什么”“系统包含哪些模块”“技术路线为什么合理”。而本文进一步回答的是“怎么把它一步一步做出来”。因此，本文档不是抽象设计说明，而是开发执行手册，强调如下四点：

\begin{enumerate}[label=\arabic*.]
    \item 先做什么，后做什么，不能乱序推进；
    \item 每个阶段的负责人是谁，产出物是什么；
    \item 用哪些工具来做，为什么这样选；
    \item 每个阶段做到什么程度，才算真正完成。
\end{enumerate}

\subsection{本文档的使用方法}

建议团队按如下方式使用本文档：

\begin{itemize}
    \item 1 号同学将本文档作为总控推进清单，每完成一个阶段就勾选一次；
    \item 2 号到 8 号各自只看与自己模块相关的章节，并把输出物按要求提交；
    \item 每次组会以本文档的阶段目标和验收标准为准，不再口头随意改范围；
    \item 若出现需求扩展，必须在不影响最小闭环的前提下再决定是否加入。
\end{itemize}

\section{实现总目标、边界与完成标准}

\subsection{实现总目标}

本项目后续实现的总目标不是做一个面面俱到的大系统，而是做一个\textbf{能稳定运行、能完整演示、能体现区块链价值、能清楚答辩}的课程项目系统。具体来说，需要达到以下结果：

\begin{enumerate}[label=\arabic*.]
    \item 能创建农产品批次并完成从农户到超市的完整流转；
    \item 能将关键数据写入 FISCO BCOS 联盟链；
    \item 能将质检报告等附件保存在链下，并通过哈希进行验真；
    \item 能按角色展示不同操作页面与不同权限；
    \item 能通过二维码或批次号查看全链路时间线；
    \item 能在监管页面检索、标记异常并查看证据链；
    \item 能在答辩演示中连续跑通至少 1 次完整闭环。
\end{enumerate}

\subsection{实现边界}

为了保证项目在课程周期内真正落地，必须主动压缩范围。以下边界原则在开发阶段不得轻易突破：

\begin{enumerate}[label=\arabic*.]
    \item 第一期只做 Web 端，不做小程序和原生 App；
    \item 第一期只做单群组，不做多群组复杂隔离；
    \item 第一期不接真实物联网设备，温湿度先由表单录入或脚本模拟；
    \item 第一期不做跨链、隐私计算、零知识证明等高难扩展；
    \item 第一期优先保证最小闭环，不追求高并发压测极限；
    \item 第一期优先做“能演示”的功能，不把时间耗在复杂美化上。
\end{enumerate}

\subsection{最终完成标准}

如果后续系统达到下面 8 条，就说明实现方案执行成功：

\begin{enumerate}[label=\arabic*.]
    \item 本地联盟链可稳定启动；
    \item 合约能部署、能写入、能查询；
    \item 注册登录和角色审核可用；
    \item 单个批次可完成四阶段业务流转；
    \item 消费者可扫码看到时间线和验真结果；
    \item 监管员可按条件检索并标记异常；
    \item 前后端联调稳定，无致命报错；
    \item 每个组员都能独立讲清楚系统链路、上链数据和区块链价值。
\end{enumerate}

\section{总体实现原则}

\subsection{原则一：先闭环，再增强}

课程项目最常见的问题不是“功能太少”，而是“功能写太多，最后一个都没跑通”。因此必须坚持先闭环，再增强。闭环优先级如下：

\begin{center}
创建批次 $\rightarrow$ 农户录入 $\rightarrow$ 加工质检 $\rightarrow$ 物流运输 $\rightarrow$ 超市上架 $\rightarrow$ 消费者查询 $\rightarrow$ 监管检索
\end{center}

只要这条链没跑通，就不允许提前花大量时间做图表大屏、物联网接入、复杂统计。

\subsection{原则二：先冻结接口，再多人并行}

多人并行开发最怕合约字段和接口反复修改。因此必须在开发初期冻结三类文档：

\begin{enumerate}[label=\arabic*.]
    \item 合约字段与函数清单；
    \item 后端 API 文档；
    \item 前端页面字段映射表。
\end{enumerate}

后续若要改，必须由 1 号统一组织讨论，不能每个人各改各的。

\subsection{原则三：区块链负责可信，数据库负责好用}

实现时要明确边界：区块链用于记录关键业务事实、状态变化、文件哈希、操作账户和时间戳；MySQL 用于条件检索、列表查询、缓存聚合、页面展示。不能把所有东西都塞到链上，也不能只写数据库不体现链上价值。

\subsection{原则四：先做稳定版本，再做展示优化}

课程答辩最怕现场演示翻车。因此后续开发阶段要先有一个“稳定但朴素”的版本，再去做样式优化、动画、图表等展示增强。

工具不是越多越好，核心是让系统稳定落地。因此建议这样使用：

\begin{enumerate}[label=\arabic*.]

\section{阶段 0：需求冻结与工程初始化}

\subsection{阶段目标}

本阶段的目标是把后续开发所依赖的“边界、字段、接口、目录、分工”全部统一，防止后面返工。

\subsection{负责人}

\begin{itemize}
    \item 主负责人：1 号；
    \item 参与人员：全员。
\end{itemize}

\subsection{使用工具}

Git、Markdown 文档、在线表格或共享文档、流程图工具（可选）。

\subsection{本阶段必须完成的事情}

\begin{enumerate}[label=\arabic*.]
    \item 明确项目只做“农户 $\rightarrow$ 加工中心 $\rightarrow$ 冷链物流 $\rightarrow$ 超市零售 $\rightarrow$ 消费者/监管员”这一固定链路；
    \item 统一 6 类角色、8 个模块与 BatchID 核心对象；
    \item 冻结状态机：\texttt{CREATED}、\texttt{FARM\_RECORDED}、\texttt{PROCESS\_RECORDED}、\texttt{LOGISTICS\_RECORDED}、\texttt{RETAIL\_RECORDED}、\texttt{SOLD/EXPIRED}；
    \item 确定哪些字段上链，哪些字段链下保存；
    \item 确定合约函数名、事件名、后端 API 名称；
    \item 初始化 Git 仓库、分支、目录；
    \item 把 8 个人的分工落实到文件级和接口级。
\end{enumerate}

\subsection{怎么做}

建议 1 号组织一次冻结会议，按以下顺序推进：

\begin{enumerate}[label=\arabic*.]
    \item 打开需求分析和系统设计文档，只允许在既有场景内细化，不允许重新扩题；
    \item 由 2 号先讲链上数据，3 到 8 号逐个确认自己模块需要哪些字段；
    \item 现场形成一张“字段来源表”：字段名、是否上链、对应模块、对应页面、是否必须查询链上；
    \item 现场形成一张“接口依赖表”：前端页面调用哪个后端接口，后端接口调用哪个合约函数；
    \item 会后由 1 号统一整理为冻结文档，发到仓库 \texttt{docs} 目录。
\end{enumerate}

\subsection{阶段产物}

\begin{itemize}
    \item 字段冻结表；
    \item 合约接口表；
    \item API 冻结文档；
    \item 页面映射表；
    \item 工程目录初始化。
\end{itemize}

\subsection{验收标准}

只要还有人说“这个字段后面再看”“这个接口先随便写”，就说明本阶段没有完成。完成标准是：\textbf{每个人都知道自己做什么、调用谁、输出给谁。}

\section{阶段 1：区块链环境搭建}

\subsection{阶段目标}

本阶段目标是把本地联盟链跑通，并完成最基础的合约部署和交易测试。没有这一层，后面所有“上链设计”都只是纸面方案。

\subsection{负责人}

\begin{itemize}
    \item 主负责人：2 号；
    \item 验收负责人：1 号；
    \item 配合人员：3 号后端。
\end{itemize}

\subsection{使用工具}

FISCO BCOS、控制台、JDK、终端、Git、可选区块链浏览器。

\subsection{要完成的具体事项}

\begin{enumerate}[label=\arabic*.]
    \item 本地搭建 4 节点联盟链；
    \item 确认节点可正常启动、出块、通信；
    \item 准备课程版单群组；
    \item 编写一个最简单的测试合约并完成部署；
    \item 能发送 1 笔交易并拿到回执；
    \item 能执行 1 次查询并看到返回结果；
    \item 记录启动方式、部署方式、常见报错和处理方法。
\end{enumerate}

\subsection{建议做法}

建议采用“\textbf{先最小跑通，再做规范化}”的策略：

\begin{enumerate}[label=\arabic*.]
    \item 先在 2 号环境上跑通 4 节点链；
    \item 将链目录、证书目录、启动命令整理成脚本；
    \item 再在 1 号机器上复现一次，确保不是“只在某一台机子能跑”；
    \item 最后输出一份 \texttt{chain-setup.md} 文档，记录每一步启动方式。
\end{enumerate}

\subsection{建议输出的文档内容}

\begin{itemize}
    \item 节点目录结构；
    \item 启动顺序；
    \item 停止顺序；
    \item 合约部署命令；
    \item 查看交易回执的方法；
    \item 常见报错及解决方式。
\end{itemize}

\subsection{阶段产物}

\begin{itemize}
    \item 可运行的 4 节点链环境；
    \item 合约部署脚本；
    \item 链环境说明文档；
    \item 交易回执截图。
\end{itemize}

\subsection{验收标准}

\begin{enumerate}[label=\arabic*.]
    \item 1 号机器能独立启动链；
    \item 可部署测试合约；
    \item 可执行写入交易并拿到回执；
    \item 可执行查询；
    \item 有一份别人看得懂的启动文档。
\end{enumerate}

\section{阶段 2：智能合约设计与实现}

\subsection{阶段目标}

将系统设计中的链上部分真正固化为可执行合约，包括角色管理、批次创建、阶段流转、异常标记、事件输出。

\subsection{负责人}

\begin{itemize}
    \item 主负责人：2 号；
    \item 配合人员：1 号、3 号、4 号、5 号、6 号、8 号。
\end{itemize}

\subsection{使用工具}

Solidity、FISCO BCOS Java SDK、合约编译工具、控制台、单元测试脚本。

\subsection{推荐合约拆分}

建议采用三合约结构：

\begin{enumerate}[label=\arabic*.]
    \item \texttt{RoleManager.sol}：负责用户注册、角色审批、启停状态、角色查询；
    \item \texttt{TraceManager.sol}：负责批次创建、农户记录、加工记录、物流记录、零售记录、状态流转；
    \item \texttt{AuditManager.sol}：负责异常标记、证据哈希、审计记录查询。
\end{enumerate}

\subsection{合约实现顺序}

合约不要一起乱写，建议按下面顺序做：

\begin{enumerate}[label=\arabic*.]
    \item 先实现角色枚举、状态枚举、基础结构体；
    \item 再实现 \texttt{createBatch()}；
    \item 再实现 \texttt{recordFarmInfo()}；
    \item 再实现 \texttt{recordProcessInfo()}；
    \item 再实现 \texttt{recordLogisticsInfo()}；
    \item 再实现 \texttt{recordRetailInfo()}；
    \item 最后实现 \texttt{flagBatch()} 与审计函数。
\end{enumerate}

\subsection{这一阶段的细节要求}

\begin{enumerate}[label=\arabic*.]
    \item 每个写入函数都必须校验角色；
    \item 每个阶段函数都必须校验上一个状态是否已经完成；
    \item 每个写入函数都必须发出事件；
    \item 批次号必须唯一；
    \item 文件哈希必须与批次绑定；
    \item 查询函数优先做概要查询和时间线查询，不要一开始就写复杂统计。
\end{enumerate}

\subsection{批次号与验真实现建议}

批次号生成建议采用：

\[
BatchID = keccak256(name \parallel originCode \parallel plantDate \parallel harvestDate \parallel creator \parallel nonce)
\]

课程实现中，前端可只显示前几位，但数据库与链上均保存完整值。

文件验真流程建议如下：

\begin{enumerate}[label=\arabic*.]
    \item 前端上传报告文件；
    \item 后端计算文件哈希；
    \item 原文件存到链下目录；
    \item 哈希与文件标识写入链上；
    \item 查询时重新计算当前文件哈希，与链上值比较；
    \item 一致则显示“验真通过”，不一致则高亮“验真失败”。
\end{enumerate}

\subsection{阶段产物}

\begin{itemize}
    \item 三份核心合约代码；
    \item 事件定义；
    \item 合约地址配置；
    \item 合约测试脚本；
    \item 合约接口文档。
\end{itemize}

\subsection{验收标准}

\begin{enumerate}[label=\arabic*.]
    \item 能创建批次；
    \item 能按正确角色推进状态；
    \item 越权调用会失败；
    \item 跳步调用会失败；
    \item 事件能被后端监听或查询；
    \item 可返回批次摘要和时间线。
\end{enumerate}

\section{阶段 4：核心业务闭环实现}

\subsection{阶段目标}

本阶段是项目实现的核心，目标是打通“农户 $\rightarrow$ 加工 $\rightarrow$ 物流 $\rightarrow$ 超市”的单批次闭环。

\subsection{负责人}

\begin{itemize}
    \item 农户模块：4 号；
    \item 加工质检模块：5 号；
    \item 物流与零售模块：6 号；
    \item 统筹联调：1 号；
    \item 合约支持：2 号；
    \item 后端支持：3 号。
\end{itemize}

\subsection{使用工具}

Spring Boot、MySQL、Java SDK、Postman、接口文档。

\subsection{实现顺序}

\subsubsection{第一步：农户模块}

要完成的事情：

\begin{enumerate}[label=\arabic*.]
    \item 创建批次；
    \item 录入基础信息、播种日期、采收日期；
    \item 录入施肥与农药记录；
    \item 生成 BatchID；
    \item 提交上链；
    \item 在页面查看当前状态。
\end{enumerate}

实现重点：

\begin{itemize}
    \item 先做单一表单提交，不要一开始拆太多复杂子页面；
    \item 农药与施肥记录可先做为摘要字段或附加文本，后续再细化；
    \item 提交成功后必须显示交易哈希和当前状态。
\end{itemize}

\subsubsection{第二步：加工与质检模块}

要完成的事情：

\begin{enumerate}[label=\arabic*.]
    \item 接收农户批次；
    \item 展示农户已提交的上游信息；
    \item 录入加工日期、清洗方式、包装规格；
    \item 录入质检员、检测结果、是否合格；
    \item 上传质检报告；
    \item 报告哈希上链；
    \item 状态推进到物流阶段。
\end{enumerate}

实现重点：

\begin{itemize}
    \item 页面上必须能看到“上游批次已存在”，否则答辩时体现不出链路连续性；
    \item 不合格状态应阻止后续正常推进，或至少在页面明确高亮；
    \item 质检报告上传成功后要能验证哈希。
\end{itemize}

\subsubsection{第三步：物流模块}

要完成的事情：

\begin{enumerate}[label=\arabic*.]
    \item 接收待运输批次；
    \item 录入车辆、司机、出发时间、预计到达时间；
    \item 录入冷链温度范围与实时温湿度；
    \item 确认送达；
    \item 提交上链；
    \item 状态推进到零售阶段。
\end{enumerate}

实现重点：

\begin{itemize}
    \item 第一阶段温湿度可用手工录入，不强求实时设备接入；
    \item 为后续监管异常准备字段：最低温、最高温、平均温；
    \item 页面要能显示是否超阈值。
\end{itemize}

\subsubsection{第四步：超市零售模块}

要完成的事情：

\begin{enumerate}[label=\arabic*.]
    \item 接收物流送达批次；
    \item 录入入库时间、上架时间、保质期、货架位置；
    \item 更新销售状态；
    \item 生成二维码；
    \item 支持标记已售、过期。
\end{enumerate}

实现重点：

\begin{itemize}
    \item 生成二维码时，二维码内容建议绑定批次查询 URL 或批次号；
    \item 上架后页面要能展示当前最新状态；
    \item 已售与过期必须改变批次状态，便于消费者与监管端识别。
\end{itemize}

\subsection{阶段产物}

\begin{itemize}
    \item 四阶段业务接口；
    \item 四阶段数据库表或详情表；
    \item 四阶段链上交易记录；
    \item 单批次全流程调试样例。
\end{itemize}

\subsection{验收标准}

\begin{enumerate}[label=\arabic*.]
    \item 创建 1 个批次后，可连续经过四阶段；
    \item 每阶段都能拿到链上回执；
    \item 数据库中能查到对应索引和交易记录；
    \item 页面上能看到状态不断推进；
    \item 任一阶段越权提交会被拒绝。
\end{enumerate}

\section{风险与应对}

\subsection{风险一：链环境不稳定}

应对方式：优先保住一套最稳定的本地环境；不要频繁更换链目录；部署脚本写好后尽量不再大改。

\subsection{风险二：合约字段频繁改动}

应对方式：阶段 0 冻结字段；后续修改必须由 1 号统一批准；禁止前后端各自理解字段。

\subsection{风险三：前后端联调对不上}

应对方式：所有接口先在 Postman 过一遍，再给前端接；前端一旦发现字段不对，第一时间回填到接口文档。

\subsection{风险四：消费者页和监管页做得太晚}

应对方式：核心闭环刚打通就立刻开做这两页，不要把全部时间花在业务端表单上。

\subsection{风险五：现场演示报错}

应对方式：准备三套兜底材料：初始化数据库脚本、固定演示数据、录屏备份。

\section{最终建议与结论}

从后续真实开发角度看，最重要的不是“写一个特别炫的系统”，而是“按正确顺序做出一个真正能跑通的系统”。因此，本项目后续推进必须始终围绕三句话：

\begin{enumerate}[label=\arabic*.]
    \item 先冻结，再开发；
    \item 先闭环，再增强；
    \item 先稳定，再展示。
\end{enumerate}

只要严格按本文给出的阶段路线推进，团队就能较稳地做出一个具备以下特征的课程项目系统：业务闭环清楚、区块链价值明确、角色划分合理、页面展示完整、监管追踪有亮点、答辩时讲得清楚、现场也跑得出来。

\section{附录 A：建议的系统启动顺序}

建议日常调试和答辩当天都按以下顺序启动系统：

\begin{enumerate}[label=\arabic*.]
    \item 启动 MySQL；
    \item 启动 FISCO BCOS 链节点；
    \item 如需使用，启动区块链浏览器或 WeBASE；
    \item 执行合约地址配置检查；
    \item 启动后端服务；
    \item 导入初始化数据；
    \item 启动前端；
    \item 用管理员账号先登录检查；
    \item 再依次测试农户、加工、物流、超市、消费者、监管页面。
\end{enumerate}

\section{附录 B：课程版最小可用闭环清单}

课程版最小可用闭环建议只盯住下面 10 个动作：

\begin{enumerate}[label=\arabic*.]
    \item 管理员审核账号；
    \item 农户创建批次；
    \item 农户提交种植信息；
    \item 加工中心录入加工信息；
    \item 加工中心上传质检报告；
    \item 物流录入运输信息；
    \item 超市入库并上架；
    \item 系统生成二维码；
    \item 消费者扫码查询；
    \item 监管员检索并标记异常。
\end{enumerate}

只要这 10 步稳定跑通，系统就已经具备了完整答辩价值。其他增强项，如图表大屏、物联网接入、多群组、多品类、移动端适配，都应放在最小闭环之后再决定是否扩展。

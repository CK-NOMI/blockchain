## ⚙️ 二、 主责功能落实：需求里的链上内容是如何实现的？

根据系统《技术方案》需求，我已在合约底层完成了数据结构字典和业务规则的像素级设计，重点实现的链上内容如下：

### 1. 唯一批次号（BatchID）生成规则
* **核心功能**：农产品全生命周期的“数字身份证”，也是前端二维码解析的唯一锚定键。
* **链上实现**：由农户调用 `createBatch` 时触发，内部通过 `generateBatchId` 函数进行哈希计算。
* **算法公式**：
  $$\text{BatchID} = \text{keccak256}(\text{农产品名称} + \text{产地} + \text{播种日期} + \text{操作账户签名} + \text{随机数})$$
* **技术特性**：生成结果为唯一的 `bytes32`（64位十六进制哈希），保证全网唯一性且不可伪造。

### 2. 需求明确要求的【链上字段结构设计】（数据字典）
我在 `TraceManager.sol` 中设计了四大结构体，将大家后续在页面上输入的内容严格锁死在链上，并由底层自动捕获 **上链账户地址 (`operator`)** 和 **操作时间戳记录 (`timestamp`)**：

* 🧑‍🌾 **阶段 1：农户录入 (`FarmInfo`)** —— 对应需求：农产品名称、品种、产地、播种/采收
  * 链上字段：名称 `name`、品种 `variety`、产地 `origin`、播种日期 `plantDate`、采收日期 `harvestDate`。
* 🏭 **阶段 2：加工质检 (`ProcessInfo`)** —— 对应需求：质检信息
  * 链上字段：加工日期 `processDate`、质检结果判定 `checkResult`、**质检报告哈希值 `fileHash`**。
* 🚛 **阶段 3：仓储运输 (`LogisticsInfo`)** —— 对应需求：运输信息与温湿度
  * 链上字段：运输车辆/物流路线 `transportData`、**实时温湿度范围 `temperature`**。
* 🏪 **阶段 4：超市上架 (`RetailInfo`)** —— 对应需求：上架信息
  * 链上字段：上架日期 `shelfDate`、保质期/过期日期 `expiryDate`。

### 3. 轻量级“哈希验真”机制
* **痛点解决**：图片、PDF 质检报告等大文件直接上链会导致区块臃肿。
* **落地策略**：质检报告 PDF 原件存在链下服务器，3号（后端）接收到文件时在 Java 端利用 `SHA-256` 算法算出文件的哈希字符串，调用 `recordProcessInfo` 将哈希值存入链上的 `fileHash` 字段。
* **验真逻辑**：消费者（7号）或监管员（8号）下载报告时，系统在本地重新计算哈希并与链上比对。哪怕报告被篡改了一个标点符号，哈希校验都会瞬间失败。

### 4. 二维码关联链上查询
* **前端（7/8号）对接**：消费者扫描超市商品上的二维码后，前端路由解析出其中的 `BatchID`。
* **后端（3号）对接**：后端直接调用合约的 `getBatchTimeLine(bytes32 _batchId)` 一键只读（View）接口。
* **链上返回**：合约会瞬间返回该批次**从播种、质检、运输（包含温湿度）到上架的所有账户地址、操作记录和哈希值**，以全链路时间轴形式完美呈现给消费端。
